# 클리어 가능성을 증명하는 랜덤 타일 문제 생성

조사일: 2026-11-13. 게임 코드는 변경하지 않았으며, 현재 POC 규칙과 1차 자료를 바탕으로 설계를 검토했다.

## 결론

가능하다. **스테이지와 함께 ‘합법적인 재단 순서 + 벽을 통과하지 않는 삽입 경로’를 생성하고, 독립 검증기를 통과한 스테이지만 제공한다.** 검증된 해법이 그 스테이지의 클리어 가능성을 보이는 증명서다.

처음에는 진입 방향이 정해진 문제군을 생성하는 것이 좋다. 이 문제군은 일반적인 경로 탐색 없이도 수식으로 풀림을 증명할 수 있다. 다양성을 늘릴 때는 먼저 해법을 만들고, 해법이 지나가는 영역 밖에만 벽을 배치하는 방식으로 확장한다.

서로 다른 두 보장을 구분한다.

- **안전성:** 제공된 모든 스테이지에는 적어도 하나의 합법적인 해법이 있다.
- **종료:** 모든 seed가 정해진 계산량 안에 스테이지를 반환한다. 이를 위해 시도 횟수를 제한하고, 실패 시 이미 증명된 기본 문제를 반환한다.

플레이어가 잘못 재단한 모든 상태에서 계속 풀린다는 뜻은 아니다. 최초 상태에서의 해법 존재를 보장하며, 잘못 자른 상태는 되돌리기·재시작으로 복구한다.

## 현재 게임에서 증명해야 하는 대상

[현재 구현](../public/games/tile-fit/index.html)의 `Geometry`, `finishCut`, `removePiece`, `tryFit`, `wallHit`, `clearTilePath`, `constrainTile`을 확인했다.

| 대상 | 필요한 조건 |
| --- | --- |
| 재단 | 실제 길이가 있는 자와 유한한 선분으로, 현재 규칙상 제거 가능한 닫힌 면을 만든다. |
| 조각 제거 | 그 시점에 존재하는 면을 실제로 선택하여 제거한다. 원하는 다각형을 선언하는 것만으로는 부족하다. |
| 남은 타일 | 원본 타일 안에 있고, 한 장으로 연결되어 있으며, 잡을 수 있는 면적·폭이 남는다. |
| 이동 | 회전 없이 평행 이동한다. 벽은 통과하지 않는다. 이미 깔린 바닥 타일은 벽 장애물로 취급하지 않는다. |
| 조작 | 작업대에서 자와 펜을 잡고 선을 그을 수 있고, 타일을 놓치지 않는 화면 내 조작 경로가 존재한다. |
| 완료 | 실제 목표 모양·위치·허용 오차를 만족하며, 자동 맞춤 애니메이션까지 벽을 통과하지 않는다. |

현재의 280×280 재료 마스크, 재단선의 두께와 면 제거 방식도 재단 결과에 영향을 준다. 또한 `wallHit`은 재료의 일부 표본점을 검사하고, `clearTilePath`는 약 3px마다 위치를 검사한다. **기존 회귀 테스트가 통과한다는 사실은 유용하지만, 연속 공간에서의 클리어 가능성을 수학적으로 증명한 것은 아니다.** 고정 간격의 검사에서 장애물을 건너뛸 수 있다는 점은 LaValle과 OMPL 문서에서도 명시한다.[2][3]

## 권장 생성 방식: 해법을 먼저 만든다

1. seed로부터 **합법적인 재단 기록**을 만든다. 닫힌 면 제거를 순서대로 실행하여 실제 남은 타일 `P`를 구한다.
2. 작업대에서 목표 자리까지의 **이동 경로 `γ`**를 선택한다. 필요한 경우 왼쪽으로 빼기 → 위로 이동 → 오른쪽으로 끼우기처럼 여러 구간으로 만든다.
3. 그 타일이 경로 전체에서 차지하는 영역 `S`를 계산한다. 벽은 `S`를 침범하지 않는 곳에만 만든다. 주변의 나머지 바닥에는 기존 타일을 배치한다.
4. 재단·이동·화면·완료 조건을 별도 검증기로 확인한다. 증명서를 통과한 후보만 제공한다.

이렇게 하면 목표 자리에 타일은 맞지만 그 자리로 접근할 수 없는 문제를 만들지 않는다. 기존 4스테이지 같은 반대 방향의 벽으로 진입을 막는 배치도 증명서를 받을 수 없다.

주의할 점은 **이동을 거꾸로 따라가는 것과 재단을 되돌리는 것은 다르다**는 것이다. 정지한 벽 사이의 이동은 경로를 역순으로 따라갈 수 있지만, 조각 제거는 되돌릴 수 있는 게임 연산이 아니다. 따라서 재단은 반드시 정방향 기록으로 검증한다. 역방향 탐색으로 풀리는 퍼즐을 만드는 선행 사례는 Taylor–Parberry의 Sokoban 생성 논문에 있지만, 그 보장을 다른 게임에 그대로 가져올 수는 없다.[7]

단순히 경로 밖에 벽을 무작위로 놓으면 벽이 멀리 있어 너무 쉬운 문제가 나올 수도 있다. 목표 위치에서 벽과 접하는 길이, 필요한 재단 수, 타일이 잘려 나가는 면적 등을 추가 필터로 사용한다. 이 필터들은 재미·난이도를 위한 것이며, 해법 증명과는 별개다.

## 첫 구현에 적합한 문제군과 보편적인 증명

아래에서 위로 끼워 넣는 문제군부터 시작할 수 있다. 타일의 로컬 좌표는 아래로 갈수록 `y`가 커지며, 원본은 `R = [0,L] × [0,L]`인 정사각형이다.

계단 또는 꺾인 직선으로 이루어진 높이 함수 `h(x)`를 무작위로 정한다. `0 < h_min ≤ h(x) ≤ h_max < L`을 만족하게 한다. 예를 들어 모서리 개수·구간 폭·높이를 seed로 선택한다. 남길 타일은 다음과 같다.

```text
P = { (x,y) ∈ R : y ≥ h(x) }
```

벽은 이 경계의 위쪽에만 둔다. 다른 벽은 삽입 통로 밖에 둔다.

**재단 가능성:** `h`의 경계선을 왼쪽 타일 가장자리부터 오른쪽 가장자리까지 유한한 선분으로 잇는다. 이 선들과 원본 타일의 위·옆 경계가 닫힌 면을 만든다. 그 위쪽 면을 제거하면 `P`가 된다. 자 길이·화면 접근 조건은 별도로 제한·검증한다. 실제 POC에 적용할 때는 재단선 두께를 포함한 결과를 다시 계산해야 한다.

**한 장 유지:** `h_max < L`이므로 모든 열이 공통으로 포함하는 아래쪽 띠 `y ≥ h_max`가 있다. 따라서 남은 타일은 연결되어 있다. `L-h_max`를 충분히 크게 제한하면 지나치게 가는 타일도 방지한다.

**이동 가능성:** 목표보다 아래로 `d ≥ 0`만큼 이동한 타일의 모든 점은 다음을 만족한다.

```text
y ≥ h(x)  ⇒  y+d ≥ h(x)
```

따라서 아래쪽 작업대에서 `d`를 연속적으로 줄여 `0`까지 이동해도 벽의 위쪽 영역을 침범하지 않는다. `d=0`에서 목표에 맞는다. **이 부등식은 특정 seed 몇 개가 아니라, 조건을 만족하는 모든 `h`에 대해 성립한다.** 이것이 이 문제군의 클리어 가능성 증명이다.

계단형뿐 아니라 대각선을 포함하는 꺾인 직선도 같은 증명이 성립한다. 문제군을 좌우 방향으로 바꿀 수도 있지만, 화면 아래의 작업대에서 옆 진입로까지 가는 경로는 추가로 확보해야 한다. 3스테이지 같은 옆 진입은 이 추가 경로가 필요한 경우다.

다양성의 한계도 있다. 이 문제군은 한 방향으로 진입할 수 있는 형태로 제한된다. 더 복잡한 오목한 형태·다중 이동 경로는 앞 절의 ‘재단과 경로를 먼저 만든 뒤 벽 생성’ 방식으로 확장한다.

## 증명서와 검증 알고리즘

스테이지 데이터와 함께 다음 정보를 보관한다. 플레이어에게 정답을 표시할 필요는 없다.

```text
rulesVersion, seed, 지원 화면 범위
초기 타일, 벽, 목표 모양·위치
cuts = [자 배치, 펜 선분, 제거할 면의 내부 클릭점, ...]
path = [재단 후 시작 위치, 중간 경유점, ..., 목표 위치]
필요하면 snap 상태와 실제 조작 입력 기록
```

검증기는 다음을 확인한다.

1. 원본 타일에서 재단 기록을 재생한다. 선분·자 길이·도구 배치가 유효한지, 클릭한 면이 당시 닫힌 면인지 확인하고 실제 재료를 제거한다. 최종 `P`의 연결성·폭·면적도 검사한다. 유한 선분들의 교차와 면은 평면 arrangement로 모델링할 수 있다.[6]
2. 이동 기록이 실제 재단 후 위치에서 시작하는지 확인한다. 각 경유점과 조작이 화면 제한 및 스냅 규칙에 맞는지 확인한다.
3. **각 이동 구간 전체**에서 타일과 벽이 겹치지 않는지 검사한다. 시작점과 끝점만 검사하지 않는다.
4. 목표 위치에서 벽과 간섭하지 않으며, 게임의 모양·위치 허용 기준과 완료 동작을 만족하는지 확인한다.

3번을 수식으로 쓰면 다음과 같다. 타일 `P`가 `q_i`에서 `q_(i+1)`로 직선 이동하는 동안 차지하는 전체 영역은

```text
S_i = P ⊕ [q_i, q_(i+1)]
```

이다. `⊕`는 두 집합의 점을 각각 더한 모든 결과인 Minkowski 합이다. 모든 `S_i`와 벽 사이에 금지된 겹침이 없어야 한다. 평행 이동만 하는 물체의 충돌을 이 방식으로 다루는 것은 구성 공간 장애물 이론의 표준적인 표현이다.[1][5]

벽과 타일의 **경계가 닿는 것**을 허용할지, 줄눈 여유를 둘지는 먼저 명세한다. 현재 게임의 의도대로 경계 접촉을 허용한다면, 경계가 닿았다는 이유만으로 충돌로 판정해서는 안 된다. 반대로 타일 면적이 벽 내부로 들어가는 것은 거부해야 한다. 안전 여유를 위해 벽을 팽창시킬 때도 최종 맞춤 접촉을 어떻게 처리할지 정해야 한다.

오목한 타일의 경우 두 끝 위치를 이은 전체 볼록 껍질이 실제 이동 영역과 같다고 가정하면 안 된다. 타일을 볼록 조각으로 분해한 뒤 각 조각의 이동 영역을 합치거나, 정확한 다각형 연산을 사용한다. 전체 볼록 껍질을 쓰는 것은 보수적으로 더 많은 후보를 거부하는 방법은 될 수 있지만, 실제 이동 영역과 동일하지는 않다.[1][5]

### 왜 이것이 증명인가

- 재단 기록을 검증했으므로 시작 상태에서 `P`를 합법적으로 만들 수 있다.
- 모든 이동 구간의 전체 영역을 검증했으므로 각 구간을 벽 통과 없이 이동할 수 있다.
- 인접 구간의 끝과 시작이 일치하므로 하나의 연속 경로로 연결된다.
- 마지막 상태가 완료 조건을 만족하므로 그 기록은 실제 해법이다.

따라서 **검증기 통과 ⇒ 적어도 하나의 해법 존재**가 성립한다. 모든 임의 후보를 풀 수 있는 만능 솔버를 만들 필요는 없다. 다만 이 증명은 명세한 기하·조작 모델과 올바르게 구현된 검증기를 전제로 한다. 검증기 구현 자체를 Coq·Lean 등으로 형식 검증하는 것은 그보다 강한 별도 과제다.

## 일반적인 솔버가 필요하다면

벽을 먼저 임의로 만든 뒤 풀리는지 찾는 방식도 가능하다. 회전이 없는 타일의 위치는 `(x,y)` 두 변수이므로, 벽을 타일 모양만큼 확장한 구성 공간에서 타일을 점처럼 이동시킬 수 있다.[1]

```text
C_obstacle = ⋃ (wall_j ⊕ (-P))
```

이 공간에서 BFS·A*로 경로를 찾는다. **찾은 모든 간선의 전체 이동을 검증했다면** 그 경로는 증명서로 사용할 수 있다. 그러나 격자에서 길을 찾지 못했다고 해서 연속 공간에도 해법이 없다는 뜻은 아니다. 가는 통로가 격자 사이에 있을 수 있다.[4]

‘임의의 후보가 풀리는지/안 풀리는지까지 완전히 판정’하려면 정확한 구성 공간 분할과 그래프 탐색 같은 완전한 계획 알고리즘을 고려할 수 있다.[8] 초기 생성기에 필요한 것은 그보다 약한 **검증된 후보만 제공한다는 보장**이다. RRT·PRM의 확률적 완전성이나 제한 시간 내 탐색은 그 자체로 모든 seed의 보장이 되지 않는다.[9]

## 현재 코드에서 먼저 정리할 것

- **권위 있는 기하 모델:** 정수 셀의 합집합 또는 정수·유리수 좌표 다각형 중 하나를 정한다. 재단·벽·목표·충돌·검증기가 같은 의미의 형상을 사용해야 한다. 렌더링만 화면 크기에 맞춰 실수로 변환한다.
- **연산의 정확성:** 정수 입력이어도 선분 교점은 유리수가 될 수 있다. 정확한 방향 판정만으로 교점 좌표 생성까지 정확해지는 것은 아니다. CGAL도 exact predicates와 exact constructions를 구분한다.[10] 무한 정밀도 정수·유리수 또는 범위가 증명된 고정 소수점 연산을 사용한다.
- **연속 이동 검사:** 현재의 표본점·3px 간격 검사를 그대로 ‘증명기’로 사용하지 않는다. 정확한 swept 영역 또는 검증된 거리·변위 상한으로 전 구간을 보장한다.[2][3]
- **조작 대응:** 물리적으로 가능한 경로만으로는 충분하지 않다. 자를 화면 밖에 놓아야 하거나, 스냅에 의해 경로를 벗어나거나, 잡은 손가락이 화면 밖으로 나가는 해법을 거부한다. 축별 이동 처리와 자동 맞춤을 포함한 실제 조작 경로를 검증한다.
- **화면 범위:** 지원할 화면 범위를 정하고 그 범위에서 작업대·도구·진입로 조건을 유지한다. 배율 변경으로 타일·벽·여유가 다르게 변하지 않게 한다.
- **실패 처리:** 후보별 seed·규칙 버전·검증 결과를 기록한다. 제한 횟수 안에 인증한 후보를 못 만들면 검증된 기본 문제로 대체한다. 계산 오류나 불확실한 판정은 통과로 간주하지 않는다.

## 조사용 계산 실험

24×24 정수 셀 모델에서 1,024개 seed의 계단형 높이 함수를 생성했다. 유한한 격자 선분을 경계로 셀의 면을 나누고 실제로 위쪽 면을 제거한 결과가 목표 재료와 같은지 확인했다. 그 뒤 각 재료 셀을 아래쪽 시작점부터 목표까지 이동시킨 **전체 직사각형 swept 영역**을 벽과 비교했다. 위치 샘플링은 사용하지 않았다. 반대로 잘못된 쪽의 면을 남기는 음성 대조군에서는 벽 겹침이 검출됐다.

이는 제안한 정수 셀 모델의 작은 조사용 실험이며, 현재 POC의 재단선 두께·스냅·모바일 입력 전체를 검증한 구현은 아니다. 1,024번의 성공을 보편적인 증명으로 삼지도 않는다. 모든 허용 높이 함수에 대한 보장은 앞의 `y+d ≥ h(x)` 불변식에서 나온다.

## 1차 자료

아래 본문·원문을 직접 확인했다. 기하 식과 이 게임의 생성 방식에 대한 증명은 해당 자료를 바탕으로 이번 조사에서 도출한 설계이며, 완성된 기존 생성기를 가져왔다는 뜻은 아니다.

1. LaValle, *Planning Algorithms*, §4.3.2, [The Translational Case](https://lavalle.pl/planning/node161.html): 평행 이동 물체의 구성 공간 장애물과 Minkowski 연산.
2. LaValle, §5.3.4, [Checking a Path Segment](https://lavalle.pl/planning/node217.html): 고정 간격 샘플링의 누락 가능성과 거리·변위 상한을 이용한 검사.
3. OMPL 공식 문서, [State Validity Checking](https://ompl.kavrakilab.org/stateValidation.html): 상태 검사와 motion 검사 구분, 이산 검사 해상도의 위험.
4. LaValle, §5.4.2, [Grid Resolution Issues](https://lavalle.pl/planning/node224.html): 격자 해상도로 인한 경로 누락.
5. CGAL 공식 문서 소스, [2D Minkowski Sums](https://github.com/CGAL/cgal/blob/master/Minkowski_sum_2/doc/Minkowski_sum_2/Minkowski_sum_2.txt): 비볼록 다각형·구멍·분해와 합집합.
6. CGAL 공식 문서 소스, [2D Arrangements](https://github.com/CGAL/cgal/blob/master/Arrangement_on_surface_2/doc/Arrangement_on_surface_2/Arrangement_on_surface_2.txt): 유한 선분이 만드는 정점·변·면.
7. Taylor & Parberry, *Procedural Generation of Sokoban Levels*, GAMEON-NA 2011, [저자 연구 페이지](https://ianparberry.com/research/sokoban/), [논문 원문](https://ianparberry.com/pubs/GAMEON-NA_METH_03.pdf): 목표에서 거꾸로 탐색하는 생성법, 인쇄 페이지 6–7. 재단의 가역성을 보장하는 자료는 아니다.
8. LaValle, Chapter 6, [Combinatorial Motion Planning](https://lavalle.pl/planning/node254.html), §6.2.2, [Vertical Cell Decomposition](https://lavalle.pl/planning/node262.html): 정확한 분할을 통한 연속 경로 문제의 유한 그래프화.
9. LaValle, [Notions of Completeness](https://lavalle.pl/planning/node182.html): 완전성과 확률적 완전성의 구분.
10. CGAL 공식 문서 소스, [Linear Geometry Kernel](https://github.com/CGAL/cgal/blob/master/Kernel_23/doc/Kernel_23/Kernel_23.txt): exact predicates와 exact constructions의 차이.

CGAL의 렌더링된 문서 사이트는 HTTP 403으로 열리지 않아 공식 저장소의 문서 원문으로 확인했다. 사용자의 브라우저를 조작하거나 게임·배포본을 변경하지 않았다.
